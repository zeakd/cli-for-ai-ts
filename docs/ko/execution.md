# 실행과 환경 연결하기

[English](../execution.md) · 한국어 · [README](../../README.ko.md)

명령은 컨텍스트를 통해 애플리케이션 서비스를 받습니다. 필요한 파일 접근, 네트워크 클라이언트, 시계를 여기에 둡니다. 영속 상태를 소유하지 않는 CLI에는 홈 디렉터리가 필요하지 않습니다.

## 실행 경계 선택하기

| API | 역할 |
| --- | --- |
| `execute(app, argv, options)` | 프로세스 IO 없이 실행하고 stdout/stderr 문자열을 수집; 테스트와 제한된 출력에 유용 |
| `executeTo(app, argv, options)` | 주입된 바이트 sink에 쓰고 매번 쓰기 완료를 기다림 |
| `cli-for-ai/node`의 `run(app, options)` | argv, stdin, 환경, 신호, 프로세스 출력 연결 |

이 API들은 효과를 실행하는 오케스트레이션이며 순수 함수가 아닙니다. 결정적인 파싱과 선언 조회에는 실행을 시작할 필요가 없습니다.

`execute`와 `executeTo`는 `context(signal)`을 받습니다. Node runner는 대신 `context({ env, cwd, signal })`을 호출합니다. `authoring<Context>()`로 핸들러의 컨텍스트 타입을 공유할 수 있습니다. 완전한 컨텍스트 주입 예시는 [테스트](testing.md)를 참고합니다.

`execute`와 `executeTo`에서 호출이 stdin을 선택한다면 `readStdin(signal)`을 제공합니다. `Promise<string>`을 반환하며 취소되면 reject해야 합니다. Node runner는 자체 reader를 제공합니다. 별도 host가 reader를 생략했는데 stdin을 선택하면 내부 오류가 나며, 조건이 맞지 않아 선택하지 않았다면 reader가 필요 없습니다. 테스트에는 `readStdin: async () => '["Ada"]'`로 제한된 입력을 공급할 수 있습니다. 실행 옵션의 선택적 `signal`로 host가 취소를 요청할 수 있습니다.

## 자원을 만들기 전에 검증하기

먼저 argv와 인자 제약을 검사합니다. 도움말·버전·거부된 입력은 컨텍스트를 만들기 전에 반환합니다. 다음으로 선택된 stdin을 읽고 검사하며, [stdin 조건](inputs.md#stdin을-읽는-조건-지정하기)이 맞지 않으면 건드리지 않습니다. 그 뒤에 컨텍스트 팩토리와 핸들러를 실행합니다.

컨텍스트를 만들었다면 `dispose(context)`를 정확히 한 번 호출하고 기다립니다. 자원을 얻은 뒤 실패하는 팩토리는 직접 그 자원을 해제해야 합니다. 페이로드 소스는 컨텍스트보다 먼저 정리하므로 사용하는 자원보다 오래 살아 있지 않습니다. 일반 결과는 dispose 전에 준비하고 정리가 끝난 뒤 반환합니다. 정리 실패 처리는 [결과](results.md)에서 설명합니다.

## 취소와 출력 소유권

첫 SIGINT 또는 SIGTERM은 실행 신호를 abort합니다. 핸들러와 소스는 취소 가능한 작업에 신호를 전달해야 합니다. 신호를 무시하는 미완료 작업은 runner를 계속 기다리게 할 수 있습니다. 일반 핸들러가 신호를 관측했다고 해서 반환한 결과를 자동으로 교체하지는 않습니다. 일반 핸들러의 취소를 보고하려면 실행 신호가 abort된 상태에서 `failed({ code: "INTERRUPTED", message: "Execution was interrupted" })`를 반환합니다. 이 조합을 종료 코드 130으로 분류하며 신호가 abort되지 않은 같은 오류는 애플리케이션 실패입니다. 일반 핸들러는 취소로 인한 reject를 잡아 해당 오류값을 직접 반환해야 합니다. AbortError나 다른 reject를 밖으로 전파하면 신호가 abort됐어도 내부 오류(종료 코드 70)입니다. 페이로드 생산의 취소 처리는 [페이로드](payloads.md#실행과-자원-소유)를 참고합니다.

Node runner는 자신이 시작한 쓰기가 끝날 때까지 기다린 뒤 오류·신호 리스너를 제거합니다. 따라서 멈춘 수신 측은 취소 후 종료도 지연시킬 수 있습니다. 두 번째 종료 신호는 출력 flush를 보장하지 않고 종료 코드 130으로 강제 종료합니다. 정상적인 `run`은 종료 코드를 반환하고 `process.exitCode`를 설정하며, 애플리케이션에 남은 핸들은 프로세스를 계속 살려 둘 수 있습니다. 같은 프로세스의 `run` 호출은 순차적으로 실행해야 합니다.

별도의 sink는 `write(chunk: Uint8Array, signal?: AbortSignal)`을 구현하고 쓰기를 수용했을 때 resolve합니다. 취소가 보고를 막지 않도록 실패 보고에는 signal을 생략할 수 있습니다. sink 백프레셔·수신 측 종료·진단은 [페이로드](payloads.md#실행과-자원-소유)에서 설명합니다.

`onDiagnostic`은 애플리케이션의 민감한 데이터를 포함할 수 있는 원인을 받습니다. 명시적으로 선택하는 기능이며 기본 동작은 고정된 공개 메시지를 사용합니다. 진단 콜백이 예외를 던져도 실행 결과를 교체하지 않습니다.

Node runner는 실행을 수락한 직후 임시 종료 코드 70을 설정하고 실행과 소유한 쓰기가 끝나면 최종 코드로 바꿉니다. 미해결 작업 외에 활성 Node 핸들이 없어 `run`이 완료되기 전에 프로세스가 끝나더라도 조용히 0으로 종료하지 않습니다. 이 장치는 프로세스를 살아 있게 유지하거나 작업을 끝내거나 오류 보고를 보장하지 않습니다. `run`은 항상 await해야 합니다. Node 24에서는 임시 종료 코드 때문에 미해결 최상위 await 경고도 출력되지 않을 수 있습니다.
